# PhilCore Desktop Approval And Presentation

Status: local Alpha digest-bound approval boundary implemented; not production-approved.

Phase: O.4

## Purpose

O.4 replaces renderer-only confirmation for sensitive desktop actions with Runtime-owned presentations and one-time approval artifacts.

The renderer may display a presentation and return approve, deny, or cancel. It does not choose digest fields, construct calldata, choose accounts, change nonce or gas fields, or generate replacement digests.

## Runtime-Owned Presentation

The main Runtime host owns:

- action kind;
- identity and session binding;
- presentation fields;
- risk classification;
- issue and expiry time;
- fresh-authentication requirement;
- canonical presentation digest;
- approval correlation.

The digest is computed over a stable Runtime canonical envelope:

```text
keccak256(stable-json-runtime-canonical-presentation)
```

This is a desktop envelope around existing Runtime presentation concepts. It does not replace ERC-4337, recovery, proof, or authorization-package digests.

## Presentation Kinds

Supported local desktop kinds:

- `local_authorization_execution`
- `user_operation_signing`
- `recovery_request`
- `recovery_cancel`
- `recovery_complete`
- `execution_owner_rotation`
- `recovery_authority_rotation`
- `validator_signing_session`
- `recovery_signing_session`
- `platform_unlock_enrollment`
- `platform_unlock_disablement`
- `local_identity_reset`

All are local-only in O.4.

## Risk Levels

Risk is generated by the Runtime host:

- `informational`
- `low`
- `sensitive`
- `critical_local`

Examples:

- platform unlock enrollment: `sensitive`
- local UserOperation signing: `sensitive`
- recovery request: `critical_local`
- recovery completion: `critical_local`
- local identity reset: `critical_local`

## Approval Artifact

An approval artifact is:

- one-time use;
- process-local;
- identity-bound;
- session-bound;
- action-kind-bound;
- digest-bound;
- expiry-bound;
- local-only;
- unavailable after restart.

Approval replay, expired approval, wrong identity, wrong session, wrong action kind, and presentation mismatch are rejected.

## Fresh Authentication

Fresh authentication is required for:

- local UserOperation signing;
- validator signing sessions;
- recovery-authority signing sessions;
- recovery request;
- recovery completion;
- execution-owner rotation;
- recovery-authority rotation;
- platform unlock disablement.

O.4 evidence classifications:

- `safe_storage_keychain_access`
- `developer_fixture`
- future `passphrase_reauthentication`
- future `webauthn_user_verified`
- future `webauthn_user_present_only`
- `unsupported`

Electron `safeStorage` evidence is not labeled biometric. Fixture evidence remains local-only.

## Local Authorization Flow

The desktop local authorization workflow now uses:

```text
local authorization presentation
  -> approval artifact
  -> real proof and UserOperation preparation
  -> exact ERC-4337 signing presentation
  -> fresh authentication evidence
  -> Device Vault validator signing
  -> local EntryPoint fixture execution
  -> audit/history
```

No public UserOperation is submitted.

This diagram records the historical O.4/O.5 composition. Current ordinary
execution stops at proof preparation because the STWO artifact is secret-
bearing and quarantined. The Runtime does not issue the signing presentation or
continue into fresh authentication, signing, or execution on that path.

## Recovery Flow

Recovery demo actions use Runtime-generated presentations and approval artifacts. Recovery request, completion, owner rotation, and recovery-authority rotation require fresh authentication. Cancellation remains a separate authority path and does not create ordinary execution authority.

## Identity Reset

Local identity reset requires:

- locked selected identity;
- Runtime-generated reset presentation;
- exact typed confirmation;
- approval artifact bound to the reset digest.
- fresh authentication or explicit passphrase reauthentication.

Private-key export is not offered.

## Limits

- O.4 does not prove biometric user verification.
- O.4 does not submit public UserOperations.
- O.4 does not deploy accounts.
- O.4 does not invoke paymasters.
- O.4 does not accept ACP-0002.
- O.4 does not approve Base Sepolia Beta.
